# Токены почтового согласования

Зависимость: параметр EmailApprovalEnabled из PR #71.

Перед включением опции установите email_approval_tokens.php вместе с активити
и выполните email_approval_tokens.sql в MySQL/MariaDB портала. Скрипт не
изменяет существующие задания. DDL не выполняется во время бизнес-процесса.

При EmailApprovalEnabled=Y уведомление каждого исполнителя получает отдельный
256-битный случайный токен в теле (ACS:...). В таблице сохраняется только
SHA-256 хеш, задание, экземпляр БП, имя активити, пользователь, email на момент
отправки, время создания, срок действия и статус PENDING. Срок — семь дней или
тайм-аут активити, если он наступает раньше. Обычная OVERDUE_DATE не считается
закрытием задания. Повторное создание токена для той же пары задание/пользователь
блокирует уникальный индекс. При возврате false из Mail::send токен отзывается.
Если создание токена не удалось, отправляется обычное уведомление и записывается
ошибка без секретов. Успех Mail::send не гарантирует доставку письма.

При N или отсутствии параметра хранилище не используется. Уже отправленные письма
и запущенные задания не получают токены задним числом. Напоминания пока отправляются
без токенов. При следующем согласовании с новым TASK_ID создаётся новый токен.

Обработчик входящих писем реализован в email_approval_handler.php. Он не является
публичной HTTP-точкой входа: подключается из доверенного PHP-правила почты.
Если таблица уже установлена на портале, повторная миграция не нужна. Если её нет,
выполнить восстановленный email_approval_tokens.sql перед включением опции. Новые статусы: PROCESSING, USED, REVIEW.
При закрытии задания или делегировании PENDING может оставаться в таблице, но
обработчик проверяет актуальное назначение и Waiting перед голосованием.

Проверка на тестовом портале: установить таблицу; проверить N и старый шаблон;
при Y и двух исполнителях проверить разные 64-символьные hex-токены и соответствие
SHA-256 в БД; проверить срок и отказ записи в БД; проверить возврат false из отправки.
Не записывать исходные токены в журнал или результаты активити.

## Подключение почтового правила

Конкретный адаптер зависит от переменных, доступных в PHP-правиле вашей версии
Bitrix. Не подставляйте предполагаемые имена переменных без проверки. Контракт:

```php
require_once '/absolute/path/to/approvecopyactiveschedule/email_approval_handler.php';
$result = \Acs\EmailApproval\ReplyHandler::handle([
    'subject' => $decodedSubject,
    'from_email' => $singleParsedFromAddress,
    'body_text' => $decodedPlainTextReply,
    'auto_reply' => $isAutomaticReply,
], $senderVerifiedByTrustedGateway);
```

Все перечисленные переменные — пример контракта, а не штатные переменные Bitrix.
Нужны уже декодированные MIME/charset поля в UTF-8. Из From требуется один адрес,
без отображаемого имени; несколько отправителей отклоняются адаптером. Для HTML
нужен разбор MIME и выделение нового текстового ответа с сохранением строк, а не
поиск команды по всему HTML. Передавайте новое содержимое ответа, по возможности
удалив цитату и подпись средствами адаптера. Не передавайте исходное MIME-письмо.
Токен извлекается из тела, включая цитату исходного письма. Тема остаётся резервным
источником для старых уведомлений. Разные токены в одном ответе отклоняются.

senderVerifiedByTrustedGateway должен быть boolean true только после проверки
отправителя вашим доверенным шлюзом/корпоративным маршрутом. Само совпадение From
или Authentication-Results, полученный от внешнего отправителя, недостаточно.
Проверку нельзя включать по наличию [ACS: в теме. При false обработчик ничего не
выполняет. Адаптер должен обнаруживать автоответы по Auto-Submitted и другим
доверенным признакам, игнорировать уведомления доставки и циклы обработки.

Первая непустая строка нового ответа — «Согласовано», «Согласовать», «Отклонено» либо «Отклонить» без учёта регистра
(допускается точка или восклицательный знак). Комментарий — только строка непосредственно после команды. Пустая строка
означает отсутствие комментария: последующие строки не подставляются вместо неё.
Строки цитаты, подписи, инструкции и токена не принимаются как комментарий.
«Не согласовано», команда в цитате и другие формулировки не принимаются. Если
комментарий обязателен, пустой ответ оставляет токен доступным для исправления.

Обработчик проверяет действующий токен и email на момент выдачи, текущий активный
профиль, Running, тип задания, workflow, имя активити и Waiting. Затем блокировка
строки FOR UPDATE атомарно меняет PENDING на PROCESSING. Решение передаётся через штатный CBPDocument::PostTaskForm с массивом задания, а активити повторно проверяет токен и исполнителя на живом БП
и предотвращает повторный голос. Подтверждённый статус исполнителя переводит
токен в USED. Неопределённый результат остаётся REVIEW/PROCESSING без автоматической
повторной отправки события. Перед ручным восстановлением сначала сверить задание
и журнал БП; не менять такие строки автоматически обратно на PENDING.

Результат completed означает подтверждённый голос исполнителя, а не завершение
всего согласования при all/vote. review_required требует ручной сверки, остальные
коды сообщают причину отказа. Результат адаптер должен писать в административный
журнал без исходных токенов, тела письма и заголовков. Письма-подтверждения пока
не отправляются.

Дополнительно проверить на тестовом портале: согласование и отклонение, обязательный
комментарий, неверный отправитель, просроченный токен, закрытое/делегированное задание,
повтор одного письма и одновременные ответы по почте/на портале, режимы all/any/vote.
Реальный вызов TaskService и выполнение внешнего события зависят от версии Bitrix.

## Штатное правило Bitrix (arMessageFields)

Адаптер email_approval_mail_rule.php использует FIELD_FROM, SUBJECT, BODY и HEADER.
Пример PHP-действия — mail_rule_action.example.php; вставить без открывающего тега
PHP и проверить путь к установленному активити. Наличие ACS: в теле маршрутизирует письмо; обработчик требует токен ACS:<64 hex символа>.
Для старых уведомлений можно временно сохранить отдельное правило по теме.

Первый режим verified_gateway требует локальный callback verify_sender, возвращающий
строго true после проверки доверенного почтового маршрута. Без него результат —
unverified_sender, задание остаётся открытым. Автоматическая проверка SPF/DKIM/DMARC
самим фильтром Bitrix не предполагается. Authentication-Results нельзя принимать
без настройки доверия к серверу, который добавляет этот заголовок и удаляет подделки.

Явно выбираемый альтернативный режим token_and_from допускает выполнение по
секретному токену и совпадению From с email исполнителя. Он не подтверждает
подлинность отправителя: утечка/пересылка токена вместе с подделкой From позволяет
передать решение. Этот режим не включён в примере по умолчанию.

В первой версии BODY должен быть обычным текстом UTF-8. HTML-only ответы и другая
кодировка отклоняются с отдельным кодом. Не применять strip_tags ко всему письму:
это может слить строки и принять текст цитаты как комментарий. Заголовок
Auto-Submitted со значением, отличным от no, и multipart/report блокируют обработку.
Проверить наличие HEADER в вашей версии; остальные признаки автоответов добавляются
в адаптер по фактическому почтовому формату. From с несколькими адресами или
разделителями отклоняется (включая некоторые сложные отображаемые имена).

Пример пишет лог в DOCUMENT_ROOT/upload/logs/acs_email_approval.log с FILE_APPEND
и LOCK_EX. Каталог создаётся при отсутствии; PHP должен иметь права записи. При
ошибке записи сообщение направляется в AddMessage2Log. Запись содержит время,
ID письма, код результата и ID задания. Доступ к файлу через веб нужно ограничить
на сервере; исходные токены, тема и тело письма в журнал не записываются. Обработчик не рассылает ответные письма.

Для выбранного режима проверка DMARC реализована в MailRuleAdapter::verifyGateway.
Укажите точный authserv_id и подтвердите gateway_strips_untrusted_results только
после проверки политики сервера. Принимается ровно один Authentication-Results от
этого сервера с dmarc=pass и header.from, совпадающим с доменом отправителя. SPF pass
сам по себе не используется. Необычные форматы заголовков консервативно отклоняются;
локальный verify_sender callback остаётся способом адаптировать доверенный шлюз.
DMARC проверяет домен отправителя, не удостоверяет конкретного сотрудника: дополнительно
по-прежнему требуются секретный токен, совпадение email и актуальное задание.

## Внутренние ответы Exchange через MAPI

Пример правила настроен на exchange_internal для наблюдаемого маршрута
MV-EXCH-OFF.nsc.ru / RV-EXCH-OFF.nsc.ru и домена tricolor.ru. Требуются ровно по
одному AuthAs=Internal, AuthSource из разрешённого списка и AuthMechanism=04,
а также Received с MAPI между разрешёнными серверами. Значение 04 здесь является
признаком наблюдаемого маршрута, а не универсальным доказательством авторства.
SMTP-отправка с механизмом 10 и другие маршруты этим режимом не принимаются.

Администратор подтвердил защиту заголовков от подделки и контроль отправки от
чужого имени. В примере правила exchange_sender_trust_confirmed установлен true
для указанного маршрута Exchange. При переносе на другой портал или изменении
коннекторов требуется повторная проверка этих условий. Заголовки сами по себе не позволяют
проверить конфигурацию коннекторов. Отправка с правами Send As подчиняется политике
Exchange: заголовки не устанавливают личность оператора отдельно от владельца From.

Ответ с Content-Type text/plain; charset=utf-8 и Content-Transfer-Encoding base64
поддерживается при условии, что Bitrix передаёт BODY уже декодированным. Повторное
base64_decode к BODY не применяется. Если BODY остаётся base64, решение будет
unknown_decision; проверить на тестовом письме и добавить декодирование только
после подтверждения контракта этой версии Bitrix. В журнал не выводить тело письма.

Комплект включает параметр, генерацию токена в уведомлении, ORM-хранилище, SQL
установки, обработчик ответа и пример почтового правила. Обновлять файлы из одной
версии ветки PR. Исходящие уведомления отправляются с CHARSET=UTF-8.

Выполнение использует CBPTaskService::GetList и CBPDocument::PostTaskForm, как в
предоставленном скрипте согласования. В стандартной реализации PostTaskForm
принимает массив задания, а не ID. Перебор вариантов действий и повторная отправка
события после неопределённого результата не выполняются. Авторизация веб-сессии
через CUser::Authorize не меняется; ID проверенного исполнителя передаётся явно.

## Результаты способа подтверждения

ConfirmationMethod — способ последнего принятого голоса: email или portal.
ConfirmationMethods — множественная строка со значениями user_<ID>:email/portal
для всех принятых голосов этого запуска активити. При all/vote список может включать
оба способа. Сообщения в журнале БП получают [По почте] или [На портале].

Новые свойства имеют пустые значения по умолчанию, изменения старых сериализованных
экземпляров выполняются только при наличии свойства. Уже принятые решения не
реконструируются. Отсутствие новых результатов не мешает работе старого процесса.
При повторном запуске активити результаты способов сбрасываются. Тайм-аут не
создаёт голос и способ подтверждения; смотреть IsTimeout отдельно.

После обновления правила поменять условие на «Тело сообщения содержит ACS:».
В новом письме перед кодом показана инструкция: ответить командой в первой строке,
сохранив исходное письмо в цитате. Исходная тема не дополняется токеном.

Переносы строк CRLF, LF и CR поддерживаются. Визуальный перенос длинной строки
в почтовом клиенте не обрезает её; фактический перенос в BODY ограничивает комментарий
первой строкой после команды. Обязательность комментария по-прежнему проверяется.


## Доработка ответом на письмо

При «С возможностью доработки» = «Да» первая строка ответа может содержать
«Доработать» или «Доработка» без учёта регистра. Комментарий — только следующая
физическая строка, как для согласования и отказа. Пустая вторая строка означает
отсутствие комментария; цитата, подпись и код согласования не используются.
Обязательность комментария проверяется по существующим настройкам (доработка
учитывается как отрицательное решение для CommentRequired=YR).

Почтовая команда передаётся через стандартную кнопку refine: RefinePressed=Y,
ConfirmationMethod=email. Доработка сразу завершает задание по отрицательной
ветке во всех режимах, включая голосование с ожиданием всех участников.
Проверка RefineAllowed выполняется по параметрам задания и повторно по живому
экземпляру БП. При отключённой опции обработчик возвращает refine_not_allowed,
токен остаётся PENDING. Повторные и поздние события не сбрасывают результат
закрытой активити.

В письмах при включённой доработке используется инструкция:

```text
Согласование по почте:
Это задание можно согласовать по почте: ответьте на это письмо словом "Согласовано", "Отклонено" или "Доработать" в первой строке. На второй строке оставьте комментарий.
При ответе не изменяйте содержимое исходного письма — сохраните его в цитате.
Код согласования: ACS:<индивидуальный токен исполнителя>
```

При выключенной доработке сохраняется прежняя инструкция. Отсутствующий
RefineAllowed в старом экземпляре трактуется как «Да», как и в существующем
интерфейсе активити. Обновить нужно approvecopyactiveschedule.php и
email_approval_handler.php вместе; схема БД и правило обработки писем не меняются.
Ранее отправленные уведомления не переотправляются.

Проверки: tests/reply_parser.php, tests/email_refine.php,
tests/notification_attachment.php и tests/mail_rule_adapter.php.
Проверка email_refine.php проходит полный путь от входящего письма через
PostTaskForm до OnExternalEvent на заглушках Bitrix: закрытие задания,
RefinePressed=Y, комментарий, режимы all/any/vote, отключённая опция,
обязательный комментарий и позднее событие.
